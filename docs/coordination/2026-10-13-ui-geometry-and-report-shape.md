# Proposal: feature-property conventions, imagery assets and report schema

Owner: Claude (consumer). Producer: Codex API. Status: **proposed, not agreed**.
Schema impact: items 1 and 3 are additive documentation of existing v1 shapes
(no version bump). Item 2 adds a field and needs `1.1.0` if accepted.

## Why

The shared fixture `fixtures/synthetic/assessment.json` has empty layers, so the
UI cannot draw a route, a cut edge or an exposed asset from it. To build and test
U02/U03/U05 the web app ships its own schema-valid fixture,
`apps/web/src/fixtures/synthetic-ui-assessment.json`
(id `synthetic-ui-geometry-001`, mode `synthetic`, generated by
`apps/web/scripts/build-ui-fixture.py`). It parses with the same v1 schema. It is
not a replacement for the shared fixture and is never sent to the API.

## 1. Feature property conventions the UI reads (no schema change)

- Stable ID: `properties.feature_id` (else `properties.edge_id`, else GeoJSON `id`).
- Road edges: the feature ID equals the `edge_id` used in
  `baseline_route_edge_ids` / `post_event_route_edge_ids` / `candidate_cut_edge_ids`.
  Optional `candidate_blocked` (bool), `length_m`.
- `status` values the map styles: roads `candidate_blocked` | `not_exposed`;
  buildings `exposed` | `not_exposed` | `unknown`; flood `candidate_flood`;
  debris `candidate_disturbance`; settlements use the settlement status enum.
- Facilities: v1 has no facility layer. The UI looks for the facility ID in any
  layer; the fixture puts the hospital in `buildings` with `amenity: hospital`.
- `flood_score` (heuristic) is shown with "not a probability". The UI never
  renders a `flood_probability`.
- `evidence_ids`, `source_id`, `method_version` as in API_CONTRACT.md.

Ask: Codex adds geometry following these conventions to the shared fixture (or a
second shared fixture), so both halves test the same features. Consumer impact:
none; the UI already reads them. Test impact: Codex fixture validation only.

## 2. Imagery assets for before/after comparison (additive, 1.1.0)

v1 lists scenes in `sources` but has no raster asset, so U03 currently shows
scene IDs and acquisition times only; no imagery is drawn. Proposed:

```json
"imagery": [
  {"asset_id": "s1-before-vv", "source_id": "...", "role": "before",
   "uri": "/api/v1/assessments/{id}/assets/s1-before-vv.png",
   "bounds": [w, s, e, n], "crs": "EPSG:4326", "sha256": "...", "rendering": "VV dB, -25..0"}
]
```

Same-origin `uri` only (no arbitrary URL fetch). Consumer change: MapView adds an
`image` source per asset, toggled by the existing Before/After control, and the
offline package caches the bytes with their hashes.

## 3. Report response schema (document existing shape)

`GET /report` is untyped in `openapi.json` (`schema: {}`). The UI validates
the shape in `services/api/src/tads_flood/reports.py`:
`assessment_id, mode, generator, ai_ready, language, facts{}, claims[{claim_id,
text, evidence_ids[]}], limitations[]`. Ask: add a Pydantic response model so
the OpenAPI export carries it; the copilot response should reuse `claims`.

## 4. Planned endpoints the UI already handles

- Jobs: `POST /assessments` may return a non-terminal job; the UI then polls
  `GET /api/v1/jobs/{job_id}` and on cancel calls `POST .../cancel`. Today
  those 404, so a non-completed job would surface as an error, not a fake result.
- Offline package: the UI builds a `browser-package-1` manifest itself
  (assets + SHA-256, scene times, attributions, report availability). A backend
  manifest endpoint can replace it; the UI verifies hashes either way.
